# SoccerBots 보상 설계

구현 위치: [`AgentSoccer.cs`](SoccerBots/Assets/Scripts/AgentSoccer.cs) / [`SoccerEnvController.cs`](SoccerBots/Assets/Scripts/SoccerEnvController.cs)
모든 shaping 가중치는 `SoccerEnvController` 인스펙터에 노출되어 있다 (프리팹 1곳 수정 → 8개 필드 전체 반영, 값 0 = 해당 항목 ablation).

---

## 0. 설계 원칙

이번 과제의 핵심 제약 세 가지를 먼저 못 박고 시작했다.

1. **shaping은 그룹 보상을 이길 수 없어야 한다.** 골이 ±1인데 shaping이 그보다 크면 에이전트는 골을 포기하고 shaping만 파먹는다. 그래서 **모든 shaping 항목에 "에피소드당 총 예산(budget)"을 걸었다.** 가중치만 작게 잡는 것으로는 부족하다 — 이벤트가 수백 번 반복되면 작은 값도 누적되기 때문이다. 예산은 코드에서 강제된다 (`m_TouchBudget`, `m_PositionBudget`, `m_StallPenaltyPaid`).
2. **위치가 아니라 변화량(델타)으로 준다.** "공에 가까우면 +"는 공 옆에 붙어 비비는 정책을 만든다. "이번 스텝에 공이 상대 골에 얼마나 가까워졌나"는 전진하는 정책을 만든다. 유일한 예외가 골키퍼 포지셔닝(G2)인데, 그 이유는 아래에 따로 적었다.
3. **farming 경로를 먼저 막고 값을 정한다.** 이벤트형 보상(볼 터치, 클리어런스)은 물리 접촉 1회가 `OnCollisionEnter`를 수십 번 발생시키므로 **쿨다운**이 없으면 공 위에 올라타 있는 것만으로 매 스텝 보상을 받는다.

## 1. 기본 보상 (base) — 원래 있던 것

| # | 항목 | 대상 | 값 | 위치 |
|---|---|---|---|---|
| B1 | 골 (그룹) | 팀 전체 | 넣은 팀 **+1**, 먹은 팀 **−1** | `SoccerEnvController.GoalTouched` |
| B2 | 골 (개별 미러) | 스트라이커 | ±1 | `SoccerEnvController.GoalTouched` |
| B3 | 존재 보상/패널티 | 스트라이커 **−1/N**, 골키퍼 **+1/N** | N = `MaxEnvironmentSteps` = 3000 | `AgentSoccer.OnActionReceived` |

B1이 POCA가 크레딧 할당을 하는 **주 신호**다. B3는 시간 압박: 타임아웃까지 끌면 스트라이커는 정확히 골 1개 값(−1)을 잃고, 골키퍼는 골 1개 값(+1)을 번다. 골 보상에 시간 할인을 **또** 걸지 않는 이유는, 그러면 시간이 이중으로 계산되어 득점한 에피소드조차 `1 − 2t/N`밖에 못 받고 커리큘럼 threshold를 못 넘기기 때문이다.

## 2. 추가 shaping 보상 — 이번에 설계한 것

### S1 — 볼 전진량 (스트라이커/팀, **델타**, 그룹 보상)

```
매 FixedUpdate:  progress = prevDist(ball, 상대골) − dist(ball, 상대골)
                 공격팀 그룹 += w × progress
                 수비팀 그룹 −= w × progress
```

| | |
|---|---|
| **가중치** | `ballProgressWeight = 0.005` / world unit |
| **예산** | 구조적으로 불필요 (아래 참조). 대신 per-step `|progress| > 2` 는 무시 |
| **총 규모** | 골대에서 골대까지 42.9u를 밀면 **+0.21** ≒ 골 1개의 1/5 |

**왜 넣었나.** 스트라이커의 **주 그래디언트**다. 골 ±1은 너무 희소해서(random policy가 골을 넣을 확률이 극히 낮다) 그것만으로는 초기 학습이 안 붙는다. S1은 "골을 넣는 방향으로 공을 미는 행위" 자체에 조밀한 신호를 준다.

**왜 델타인가.** 위치형("공이 상대 진영에 있으면 +")은 공을 밀어놓고 가만히 있어도 계속 적립된다. 델타는 **왕복하면 정확히 0**이라 진동으로 파밍할 수 없다. 공을 앞뒤로 흔들어도 순증이 0이면 보상도 0이다.

**왜 예산이 없어도 되나.** 두 팀에 정확히 부호만 반대로 주므로 **zero-sum**이고, 시간에 대해 telescoping이라 에피소드 총합은 `w × (시작거리 − 종료거리)` 로 **경로와 무관하게 시작·끝 위치만으로 결정**된다. 즉 아무리 오래 굴려도 상한은 피치 길이 × w = 0.21이다. 이 상한을 실제로 받으려면 공을 상대 골문까지 몰고 가야 하는데, 그건 곧 득점이다.

**스케일 근거.** 0.005 × 42.9 = 0.21. 골(±1) 대비 21%. "shaping < 그룹 보상" 조건을 만족하면서, 초반에 골이 거의 안 터지는 구간에서는 사실상 유일하게 살아있는 신호가 되도록 충분히 크게 잡았다. 0.001까지 줄이면 총 0.043으로 존재 패널티(−1)에 묻힌다.

**리셋 처리.** 골/타임아웃 후 공이 순간이동하면 거리가 급변한다. `ResetScene()` 끝에서 `m_PrevBallDistToRedGoal`을 **리스폰 이후 위치로 재기준화**하고, 추가로 per-step 2u 초과 변화는 무시한다.

### S2 — 스트라이커 볼 터치 (개별, 이벤트, 쿨다운)

| | |
|---|---|
| **가중치** | `strikerTouchWeight = 0.005` / 터치 |
| **쿨다운** | `touchRewardCooldown = 0.5초` |
| **예산** | `strikerTouchBudget = 0.1` / 에피소드 (= 최대 20터치) |

**왜 넣었나.** S1은 **공이 이미 움직이고 있어야** 신호를 준다. 아직 공 근처에도 못 가는 초기 정책에게는 S1의 그래디언트가 0이다. S2는 "일단 공에 닿아라"라는 한 단계 앞의 부트스트랩이다. 이게 붙어야 S1이 일을 시작한다.

**왜 이 크기인가.** 예산을 다 채워도 0.1 = 골 1개의 1/10. 공만 툭툭 건드리고 다니는 정책은 골을 넣는 정책을 **절대 이길 수 없다**. 반대로 존재 패널티(에피소드 −1)보다는 크므로 "가만히 있느니 공을 건드리자"는 유인은 확실히 생긴다.

**쿨다운이 왜 필수인가.** 물리 접촉 1회가 `OnCollisionEnter`를 매 물리 스텝 발생시킨다. 쿨다운 없이는 공 위에 올라타 있는 것만으로 50회/초 × 0.005 = **0.25/초**가 적립된다 — 골 보상의 15배. 0.5초 쿨다운 + 예산 20회로 두 겹 방어했다.

> 기존 구현에 있던 방향성 성분(`relativePosition.x × 0.01`)은 제거했다. S1이 같은 일을 더 정확하게(공의 실제 이동으로) 하므로 중복이고, 두 신호가 어긋날 때 원인 추적이 어려워진다.

### G1 — 골키퍼 클리어런스: 공을 **멀리** 걷어냈을 때 (개별, 이벤트, **델타**)

```
골키퍼가 공에 접촉  → 측정 윈도우 오픈 (현재 공-자기골 거리 기록)
50 스텝(=1초) 후    → gained = dist(ball, 자기골) − 시작거리
                      gained > 0 이면  reward = w × clamp01(gained / 15)
```

| | |
|---|---|
| **가중치** | `goalieClearanceWeight = 0.02` / 클리어런스 (최댓값) |
| **윈도우** | `goalieClearanceWindow = 50` 스텝 (1초) |
| **기준 거리** | `goalieClearanceRefDist = 15u` 를 벌면 만점 |
| **예산** | `goalieClearanceBudget = 0.1` / 에피소드 (= 완벽한 클리어 5회) |

**왜 넣었나.** 팁에 나온 "골키퍼: 공을 멀리 찼을 때 +" 그대로다. 그리고 **접촉 자체에는 보상을 주지 않는 것이 핵심**이다. 막기만 하고 공이 발 앞에 떨어지면 그건 세이브가 아니라 **리바운드**고, 다음 순간 다시 먹힌다. 그래서 접촉 시점이 아니라 **1초 뒤 공이 실제로 어디까지 갔는지**로 지급한다.

**왜 델타인가.** "공이 내 골에서 멀리 있으면 +"라는 위치형으로 주면 골키퍼는 공이 반대 진영에 있는 동안 공짜 보상을 계속 받는다 — 자기가 한 일이 없는데도. 접촉 시점을 기준으로 한 델타는 **골키퍼가 실제로 만들어낸 변화만** 지급한다.

**스케일 근거.** 이전 구현은 접촉 1회당 최대 0.15(= 골의 15%)를 즉시 지급했고 쿨다운도 예산도 없었다. 골키퍼가 공에 붙어 비비면 무한 파밍이 가능했다. 0.02 + 예산 0.1로 낮춰서, 한 에피소드 내내 완벽하게 걷어내도 골 1개의 1/10이다.

### G2 — 골키퍼 블로킹 포지션 (개별, per-step, 예산 캡)

```
이상 지점 = 자기 골 중심 + normalize(공 − 자기 골) × 4.5
매 스텝    err = clamp01(dist(골키퍼, 이상지점) / 10)
           penalty = (예산 / N) × err          // N = 3000
```

| | |
|---|---|
| **예산** | `goaliePositionBudget = 0.15` / 에피소드 (per-step 5×10⁻⁵) |
| **standoff** | `goalieStandoff = 4.5` → 골 중심(로컬 x ±21.45)에서 4.5 나오면 **로컬 x ∓16.95 = 골키퍼 홈 라인(±17)** |
| **기준 거리** | `goaliePositionRefDist = 10u` 벗어나면 최대 페널티 |

**왜 넣었나.** 골키퍼는 "자기 골과 공을 잇는 선 위"에 있어야 슛 각도를 막는다. 이상 지점을 **골–공 직선 위의 한 점**으로 잡으면 깊이 유지(골라인 지키기)와 좌우 트래킹(공 각도 따라 슬라이딩)이 **한 항으로 동시에** 나온다. 항을 두 개 만들 필요가 없다.

**왜 여기만 위치형인가.** 팁 #2("위치 보상보다 변화량")의 예외다. 스트라이커에게 "공 근처에 있어라"는 공을 안 차는 정책을 만들지만, **골키퍼는 자리를 잡는 것 자체가 임무**다. 델타로 주면("이상 지점에 가까워지면 +") 오히려 이상 지점 주변을 왔다갔다 하며 접근-이탈을 반복하는 파밍이 생긴다. 대신 안전장치를 예산으로 걸었다: 온 필드를 헤매도 에피소드 총 −0.15, **실점(−1)의 15%**를 넘지 못한다.

**스케일 근거.** 이전 구현은 `−existentialReward × strayed` 였는데, `existentialReward = 1/50000`, `strayed`가 최대 40이면 스텝당 −8×10⁻⁴, 50000스텝이면 **총 −40**. 골 신호의 40배로 완전한 스케일 붕괴였다 (골키퍼가 실점을 감수하고서라도 라인에만 붙어있는 게 최적). 예산 기반으로 바꿔 −0.15로 고정했다.

### (부수) 볼 스톨 페널티 — VsGoalie 커리큘럼 전용

공이 2초 이상 멈춰 있으면 공격 그룹에 지수적으로 커지는 페널티. 스트라이커가 뒤에 있는 공을 안 주우러 가는 실패 모드를 겨냥한 것이라 그대로 뒀지만, 예산을 **1.0 → 0.1**로 낮췄다. 기존 1.0은 골 1개 값 전체라 `Striker Group Cumulative Reward`를 통째로 끌어내렸다.

## 3. 스케일 요약 — shaping이 그룹 보상을 이기지 못하는지 검산

| 항목 | 에피소드 최대 절댓값 | 골(±1) 대비 |
|---|---|---|
| B1 골 (그룹) | 1.0 | 100% (기준) |
| B2 골 (개별 미러, 스트라이커) | 1.0 | 100% |
| B3 존재 (타임아웃 시) | 1.0 | 100% |
| **S1** 볼 전진 | 0.21 | 21% |
| **S2** 스트라이커 터치 | 0.10 | 10% |
| **G1** 골키퍼 클리어런스 | 0.10 | 10% |
| **G2** 골키퍼 포지션 | 0.15 | 15% |
| 볼 스톨 (VsGoalie만) | 0.10 | 10% |

- 스트라이커가 받을 수 있는 shaping 총합: **S1 0.21 + S2 0.10 = 0.31**
- 골키퍼가 받을 수 있는 shaping 총합: **G1 0.10 + G2 0.15 = 0.25**

둘 다 골 1개(±1, 스트라이커는 그룹+개별로 사실상 ±2)보다 확실히 작다. **shaping을 최대로 파먹는 정책보다 골 1개를 넣는 정책이 항상 이긴다.**

## 5. 검증 방법 (ablation)

각 항목의 가중치/예산을 0으로 두면 그 항목만 꺼진다. 팁 #3("한 번에 하나씩")에 맞춰 이 순서로 확인했다.

| 단계 | 켜는 것 | 보는 지표 |
|---|---|---|
| 0 | base만 (S1·S2·G1·G2 = 0) | 기준선. 골이 거의 안 터지는지 확인 |
| 1 | + S2 | `Striker/Environment/Cumulative Reward`가 0.1 근처에서 포화 → 터치는 배웠으나 골은 아직 |
| 2 | + S1 | 보상이 0.1 위로 계속 상승 → 공을 전진시키기 시작 |
| 3 | + G1, G2 | `Goalie/Environment/Cumulative Reward`, `Self-play/ELO` |

**이상 신호로 볼 것:**
- `Cumulative Reward`가 shaping 예산 총합(스트라이커 0.31 / 골키퍼 0.25) 근처에서 **평평해지면** → shaping farming. 골을 안 넣고 있다는 뜻.
- `Policy/Entropy`가 급락 → 특정 파밍 행동으로 조기 수렴.
- `Self-play/ELO`가 안 오르는데 `Cumulative Reward`만 오르면 → shaping만 늘고 실력은 그대로.

## 6. 학습 실행

### 환경 함정 두 가지 (둘 다 실제로 밟았음)

**1. `soccer.yaml`에 한글/유니코드를 쓰면 학습이 시작조차 안 된다.**
`mlagents-learn`은 YAML을 UTF-8이 아니라 **OS 기본 코덱**으로 연다 (`cli_utils._load_config`). 한글 Windows면 cp949라 UTF-8로 저장된 한글·em-dash·화살표에서 바로 죽는다.

```
UnicodeDecodeError: 'cp949' codec can't decode byte 0xe2 ...
TrainerConfigError: There was an error decoding Config file ... Make sure your file is save using UTF-8
```

→ `soccer.yaml`은 **ASCII 전용**으로 유지하고, 설계 근거(한글)는 이 문서에 둔다.

**2. `threaded: true` + CUDA 조합은 크래시한다.**

```
RuntimeError: Expected all tensors to be on the same device,
but found at least two devices, cuda:0 and cpu!
```

원인: PyTorch 2.x의 `torch.set_default_device()`는 **스레드 로컬**이다. ml-agents는 import 시점에 메인 스레드에서 `set_default_device('cuda')`를 호출하는데, `threaded: true`면 트레이너 업데이트가 **별도 스레드**에서 돌고 그 스레드는 기본 디바이스를 물려받지 못해 CPU 텐서를 만든다 → 모델(cuda)과 불일치.

```python
torch.set_default_device('cuda')
torch.zeros(2).device            # cuda:0  (메인 스레드)
# 워커 스레드에서:  torch.zeros(2).device  ->  cpu
```

`--torch-device=cpu` 로도 못 고친다. ml-agents의 `set_torch_config()`가 CPU 경로에서 `set_default_device`를 **되돌리지 않기** 때문에 import 때 걸린 cuda 설정이 그대로 남는다. 확실한 해결은 프로세스에서 CUDA 자체를 숨기는 것:

```bash
CUDA_VISIBLE_DEVICES=-1 mlagents-learn ...
```

(관측이 벡터/레이 센서뿐이라 512x2 MLP는 CPU가 오히려 빠르다. GPU를 쓰려면 `threaded: false`로 둘 것.)
